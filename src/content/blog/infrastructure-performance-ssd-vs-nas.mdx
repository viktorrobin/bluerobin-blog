When I first moved my PostgreSQL database to the NAS over NFS, I could not understand why queries that took 2ms locally were suddenly taking 40ms. I spent an entire weekend running `fio` benchmarks, tweaking NFS mount options, and comparing iSCSI versus NFS paths before realizing that the problem was not bandwidth but latency -- the 0.8ms round-trip penalty on every random 4K read was compounding across thousands of B-tree lookups per query. That experience fundamentally changed how I think about storage placement in Kubernetes: it is not about how fast you can stream a large file, but about how many tiny random reads your storage can serve per second. This article distills those benchmarks and the workload placement strategy that emerged from them.

## Introduction

In a homelab or on-premise Kubernetes cluster, storage is often the biggest bottleneck. We have two main storage tiers available:

1. **Local NVMe SSDs**: Directly attached to the compute nodes (PCIe Gen4).
2. **Network Attached Storage (NAS)**: Accessed via 10GbE network (TrueNAS Scale over NFS/iSCSI).

The question is: **Which workload goes where?**

### What We'll Measure

We will use `fio` to benchmark both paths from within a Kubernetes Pod to simulate real-world conditions.

<ExternalCite title="fio - Flexible I/O Tester Documentation" url="https://fio.readthedocs.io/en/latest/" author="Jens Axboe" date="2024-02-01" />

## Architecture Overview

We use **Longhorn** as our Block Storage provider, but configured differently for each tier.

- **Fast Path**: Longhorn utilizing `hostPath` on NVMe. Good for Databases.
- **Bulk Path**: NFS mount backed by TrueNAS ZFS. Good for MinIO/Backups.

## Section 1: The Benchmarks

We ran `fio` with random read/write patterns (4k block size) to simulate database traffic, and sequential patterns (1M block size) for file streaming.

### Local NVMe (WD Black SN850X)

```bash
fio --name=random-write --ioengine=libaio --rw=randwrite --bs=4k --numjobs=1 --size=4g --iodepth=32
```

- **IOPS**: ~650,000
- **Latency**: 0.04ms
- **Bandwidth**: ~2.5 GB/s

### 10GbE NAS (NFS over TrueNAS)

- **IOPS**: ~45,000
- **Latency**: 0.8ms (Network overhead)
- **Bandwidth**: ~980 MB/s (Saturation of 10GbE line)

<ImplementationNote title="Unexpected NFS performance regression">
My first round of NAS benchmarks showed only 15,000 IOPS instead of the 45,000 I expected. The bottleneck turned out to be ZFS's default recordsize of 128K, which caused massive read amplification for 4K random workloads. For the iSCSI zvol backing database volumes, I set the volblocksize to 8K to match PostgreSQL's page size. For the NFS dataset serving MinIO, I kept the default 128K recordsize since object storage performs sequential I/O. This single tuning change tripled my random IOPS on the NAS path and taught me that storage benchmarks are meaningless unless you account for the filesystem layer.
</ImplementationNote>

<ExternalCite title="ZFS Performance Tuning Guide" url="https://openzfs.github.io/openzfs-docs/Performance%20and%20Tuning/Workload%20Tuning.html" author="OpenZFS" date="2024-01-15" />

<Callout type="info" title="Latency is King">
    While 980 MB/s sequential speed is great, the 0.8ms latency kills database performance for transactional workloads.
</Callout>

## Section 2: Workload Placement Strategy

Based on these numbers, we split our infrastructure.

### Databases (PostgreSQL, Qdrant, FalkorDB)
**Placement**: Local NVMe.
**Why**: Vector search and graph traversals are random-access heavy. High IOPS and low latency are critical for "snappy" searches.
**Mechanism**: We use Kubernetes `LocalPersistentVolumes` or Longhorn with strict node affinity to keep data close to the CPU.

<ImplementationNote title="Node affinity vs data locality trade-offs">
I initially used Longhorn's `strict-local` data locality for PostgreSQL, which pinned the volume to a single node. This worked perfectly for performance, but when that node needed a kernel upgrade and had to reboot, the database was completely unavailable for 12 minutes while the node came back. I switched to `best-effort` locality with 2 replicas instead. The random read performance dropped by about 8% due to occasional cross-node reads, but the database now survives node restarts by failing over to the second replica within seconds. For my homelab workloads, 8% slower reads are a far better trade-off than 12-minute outages.
</ImplementationNote>

### Object Storage (MinIO) & Backups
**Placement**: NAS (NFS/iSCSI).
**Why**: Documents (PDFs, Images) are read sequentially. A 20MB PDF loads in 0.02s over 10GbE, which is imperceptible to the user.
**Scale**: The NAS offers 40TB of redundancy (RAIDZ2), which NVMe cannot match cost-effectively.

<ExternalCite title="Kubernetes Storage Best Practices" url="https://kubernetes.io/docs/concepts/storage/storage-classes/" author="Kubernetes Authors" date="2024-06-01" />

<ImplementationNote title="Measuring real application latency, not just fio">
After seeing the fio numbers, I assumed my workload placement was optimal and moved on. Months later, I noticed that RAG queries against my Qdrant vector database were taking 200ms when they should have taken 50ms. The fio benchmark had tested sequential patterns, but vector similarity search performs random reads across the entire HNSW index. I added Prometheus histograms to track per-query storage latency from within the application, and that revealed the NAS path was being used for some Qdrant shards due to a misconfigured StorageClass selector. Always validate benchmarks against real application behavior.
</ImplementationNote>

## Section 3: Configuring Kubernetes

To implement this, we define two StorageClasses.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-nvme
provisioner: driver.longhorn.io
parameters:
  dataLocality: best-effort
  numberOfReplicas: "1" # Rely on app-level replication or backups
  diskSelector: "nvme"
---
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: bulk-nas
provisioner: nfs.csi.k8s.io
parameters:
  server: 192.168.0.50
  share: /mnt/tank/k8s
```

## Conclusion

Don't treat all storage as equal. By mapping workloads to the physical characteristics of the storage medium, we get the best of both worlds: extreme database speed and massive, cheap capacity for files.

The biggest takeaway from this benchmarking exercise was that raw throughput numbers tell only half the story. What actually matters is how your specific workload interacts with the storage path: random vs sequential, small vs large blocks, read-heavy vs write-heavy. I now run application-level latency benchmarks alongside fio whenever I change storage configurations, because a 10x improvement in fio numbers means nothing if the application's access pattern does not benefit from it.
